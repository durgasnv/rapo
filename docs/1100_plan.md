# rapo. — Technical Implementation Plan

**Approach:** Modular monolith first; separate frontend, API, grouping module, and scheduled worker. Avoid premature microservices.

## 1. Stack
| Layer | Choice | Reason |
|---|---|---|
| Frontend | Next.js + TypeScript + Tailwind CSS | Accessible, responsive UI and typed application code |
| Backend | FastAPI + Python + Pydantic | Typed REST API and natural fit for grouping algorithm |
| Database | PostgreSQL | Relational integrity, transactions, historical pair queries |
| ORM/migrations | SQLAlchemy 2.x + Alembic | Explicit models and repeatable schema changes |
| Auth | Secure server-side sessions or short-lived JWT + refresh flow | Controlled authentication with role-based authorization |
| Grouping | Python heuristic initially; OR-Tools optional | Transparent scoring and constraint solving |
| Background jobs | Scheduler + worker with DB-backed idempotency | Three-day grouping and notifications |
| Tests | Pytest, HTTPX, Playwright | Unit, integration, and E2E coverage |
| Deploy | Vercel + Render/Railway + managed PostgreSQL | Straightforward public deployment |

## 2. High-level architecture
```text
Browser (Next.js)
    |
    v
FastAPI REST API -- Auth / RBAC / Event state machine
    |                |
    |                +-- Grouping service (Python)
    |                +-- Notification service
    v
PostgreSQL <---- Scheduled worker (due-event checks)

Grouping preview -> organizer approval -> transactional finalization
```
Frontend must not calculate authoritative group assignments. Backend owns validation, grouping, and all state changes.

## 4. Data model
- `users(id, name, email UNIQUE, password_hash, created_at)`
- `events(id, organizer_id FK, title, description, timezone, start_at, end_at, registration_opens_at, registration_closes_at, grouping_at, capacity NULLABLE, min_team_size, max_team_size, confirmation_deadline, status, version, created_at)`
- `registrations(id, event_id FK, user_id FK, status, registered_at, waitlist_position NULLABLE, UNIQUE(event_id,user_id))`
- `grouping_runs(id, event_id FK, status, algorithm_version, random_seed, score, explanation_json, created_by, created_at)`
- `teams(id, event_id FK, grouping_run_id FK, status, created_at)`
- `team_members(id, team_id FK, user_id FK, confirmation_status, assigned_at, UNIQUE(team_id,user_id))`
- `collaboration_pairs(user_a_id, user_b_id, completed_event_count, updated_at)` as optional cached projection; enforce ordered IDs (`user_a_id < user_b_id`). Derive from completed teams or update transactionally on completion, never double count.
- `audit_logs(id, actor_id, event_id, action, before_json, after_json, created_at)`
- `notifications(id, user_id, type, payload_json, read_at, created_at)`

**Integrity:** DB-level unique constraints, foreign keys, check constraints for team size config, and transaction-safe event state updates. For a participant's one-team-per-event invariant, enforce within a serialized finalization transaction and optionally denormalize event_id into `team_members` with `UNIQUE(event_id,user_id)`.

## 6. Grouping algorithm
### Inputs
Eligible registrations, team size range, pair-frequency map from prior completed events, seed, optional event-specific constraints.

### Feasibility first
Find a team count `k` satisfying `k * min_team_size <= N <= k * max_team_size`. If none exists, return a typed infeasibility response with recommended adjustments. If `N=0`, report no eligible participants.

### Objective
For each team `T`, define repeated-pair cost:

`cost(T) = sum(frequency(a,b) for all unordered pairs a,b in T)`

Minimize total cost, optionally adding a small fairness penalty for concentrating repeated pairings on a few participants. All hard constraints are mandatory; optimization never overrides them.

### MVP heuristic
1. Calculate valid team-size partitions.
2. Construct seeded initial assignments with lower-frequency pair preference.
3. Improve via member swaps and moves that preserve size limits.
4. Repeat for a bounded number of deterministic seeds/iterations.
5. Return best valid result with score, per-team pair penalties, and reproducible seed.
6. For small participant counts, compare against exact/brute-force results in tests; later use OR-Tools for stronger optimization.

**Complexity guardrails:** Cap participants and compute time for MVP; run expensive grouping asynchronously and report job progress. Never claim global optimality for a heuristic.

## 7. Event workflows
### Registration
Lock or atomically update event capacity; create `REGISTERED` or `WAITLISTED` registration. Enforce one registration per user/event. Promote oldest eligible waitlisted user after an eligible cancellation before grouping.

### Scheduled grouping
Worker scans due events (`grouping_at <= now`, registration closed, not already processed), acquires a DB lock/lease, runs grouping, and stores a proposal. Organizer reviews before finalization. Schedule defaults to three days before event start but cannot precede registration close.

### Finalization
Inside one transaction, lock event, verify proposal matches current eligible registration version, ensure all hard constraints, create teams/members, transition status, write audit entry, commit. Reject stale proposals and require regeneration.

### Post-finalization dropout
Record withdrawal, notify organizer, offer eligible waitlisted replacement, and validate resulting team size. If no feasible replacement exists, mark team `NEEDS_ATTENTION` and require explicit organizer action; do not silently accept invalid teams.

## 8. Security and privacy
- Password hashing with Argon2/bcrypt; email normalization; login rate limits.
- Prefer HttpOnly, Secure, SameSite cookies for browser sessions; CSRF protection for cookie-authenticated writes.
- Enforce owner/member checks at every endpoint; never trust role flags from client.
- Secrets in deployment secret manager; least-privilege DB credentials.
- Restrict team membership visibility; audit administrative overrides.
- Avoid exposing email addresses in public rosters.

## 9. Testing strategy
- **Unit:** Team count feasibility, pair scoring, deterministic tie-breaks, swap logic, all-worked-together case.
- **Property-based:** No duplicates; exact coverage of eligible participants; every team within range; reproducibility for same seed.
- **Integration:** Database migrations, auth, capacity race, FIFO waitlist, stale proposal rejection, concurrent finalization.
- **E2E:** Organizer creates event → participants register → grouping preview → finalize → confirmations → withdrawal/replacement.
- **Load:** Measure registration burst and grouping runtime at chosen participant limits.

## 10. Deployment and operations
1. Provision managed PostgreSQL; apply Alembic migrations.
2. Deploy FastAPI and scheduled worker (Render/Railway or equivalent); configure CORS and secrets.
3. Deploy Next.js frontend to Vercel; configure API URL and HTTPS.
4. Add health/readiness endpoints, structured logs, error tracking, database backups.
5. Seed a demo organizer, demo participants, completed historical events, and an active event (clearly marked demo data).
6. Configure GitHub Actions: lint, type checks, backend tests, frontend tests, build; deploy after passing checks.
7. Document environment variables, rollback procedure, and operational limits.

## 11. Definition of done
A new user can sign up, register, get assigned to a valid team, confirm, and see their team on a publicly deployed site. An organizer can reproduce grouping decisions, handle dropouts, export rosters, and inspect audit logs. Automated tests cover key invariants and concurrency.
